## 開発時のルール

### 共通

- コードコメントは極力書かない。書く場合は「何をしているか」ではなく「何故そうしているか」という観点で記載すること
- コードコメントやメッセージ等は全て日本語で書くこと

### JavaScript/TypeScript プロジェクトの場合

#### 命名規則

- ディレクトリ名やファイル名はケバブケースとすること
- 変数名
  - 「値が動的（実行時に決定）」な場合はキャメルケース、「値が静的（実行前に決定、かつ不変）」な場合はアッパースネークケースとすること
  - `data`や`value`など、格納される値が推測し辛い抽象的な名称は用いず、極力具体的かつ冗長過ぎない名称にすること
- テスト用のファイルは`**.test.ts`という名称にすること

#### 型定義に関するルール

- 関数やメソッドの返り値の型は極力明示せず、推論に任せること
- `any`や`as`による型キャストは利用しないこと
- オブジェクトかつ前述のような静的な変数に対しては`as const`を付与すること

#### その他

- import 文は絶対パスは利用せず、必ず import alias を利用して`@/`の形から始めること
- パッケージ管理に利用しているツールは以下から判断し、適切なコマンドを使用すること
  - ルートに`package-lock.json`が存在 -> `npm`を使用
  - ルートに`yarn.lock`が存在 -> `yarn`を使用
  - ルートに`pnpm-lock.(yaml/yml)`が存在 -> `pnpm`を使用
  - プロジェクトが workspace 化されている場合、git 管理におけるルートディレクトリまで戻り lock ファイルを確認すること

### GitHub の利用ルール

- commit メッセージには,chore, fix, feat, docs のいずれかのプレフィックスを利用する。
- commit メッセージは日本語で何をなぜ変更したのか記載する
- 非常に小さい粒度で定期的にコミットする
- Lint, test, typecheck を CI で基本的に確認するため Push する前にローカルで成功することを確認する
- CI にエラーがある限り PR がマージされることはない
- ブランチは feat, fix, docs, chore 等のブランチから始まり、issue 番号を明記する。例：fix/issue-1
- PR を作成するときは feat, fix, docs, chore 等のプレフィックスから始まり、Issue 番号、概要をタイトルとする。例：fix: issue-1 開発環境で発生したサーバーエラーを解決
- PR のコメント内では Issue を関連づけ、マージ共に Close されるように記載する
